How this log is kept current

This file lives at docs/BUILDLOG.html and is updated as part of every factory session, committed with the batch it describes:

  1. After each batch or incident: add an incident card (symptom → root cause → fix → lesson), update the ledger, stats, and the Last updated stamp.
  2. Numbers come from the tools, never from memory: tickets/runs from factory.db, PRs from gh pr list --state all, commits from git log.
  3. Incidents are grouped by category — sandbox pipeline agent behavior ticket spec infrastructure — and numbered so they can be referenced (S1, P3, A1, T2…).
  4. Commit message convention: docs: build log — <what changed>.

Incident log — what broke and what it taught us

Every entry is a real failure from a real run, in the order it was hit. This is the most valuable section of the repo.

Sandbox & security

S1 · The agent could read your tokens and write outside the worktree sandbox

Symptom run_command was the one shell surface — and it inherited the full environment (GitHub token included) and allowed shell redirection to any path on disk.

Root cause Default-trust subprocess: subprocess.run(shell=True) with no env filtering; deny-list covered commands, not redirection.

Fix Allowlisted environment (PR #6) — the agent gets PATH and nothing else; redirection outside the worktree refused; path guards resolve every path and reject escapes and .git.

Lesson An agent's environment is part of the blast radius. Default-deny env, then add what's proven needed.

S2 · The human gate was silently dead sandbox

Symptom Every change rated low blast radius, so nothing ever needed David's approval — including changes to the gates themselves.

Root cause Blast radius was computed from the diff after the worker's commit, so the diff was always empty.

Fix Capture the base SHA before committing and classify against it. Caught by tests/smoke.py — the smoke test earned its keep on day one.

Lesson A security control that fails silently is worse than none. Test gates against a change that must trip them.

S3 · Secret scanner flagged the whole checkout sandbox

Symptom Runs blocked on "secrets" that were already in the repo (test fixtures, docs).

Fix Scan only the lines a change adds, not the whole tree.

S4 · The factory ran with your whole GitHub account sandbox

Symptom Pushes used the ambient gh credential — full account scope for a bot that only needs to push agent/* branches and open PRs on one repo.

Fix Fine-grained scoped credential (PR #4), proven with live permission/scope probes before trusting it. Worker uses it, not your login.

S5 · A "tests" PR passed CI with zero tests — and shipped Windows system binaries sandbox

Symptom PR #37 (ticket 13) merged-clean on all checks. Diff: one scratch file and six Windows system-cache binaries — the agent had written to a literal %SystemDrive%\... path inside the worktree and committed whatever landed.

Root cause Gates checked "tests pass" and "no secrets" — nothing checked that a test ticket produced tests, or that the diff was text.

Fix Junk gate in the worker: reject any diff containing binary files; reject a test-ticket whose diff touches no file under tests/. Both fail the attempt, so the ticket retries instead of dying.

Lesson Green CI ≠ correct change. Gates must assert the ticket's intent, not just hygiene.

Pipeline correctness

P1 · Failed pushes reported success pipeline

Symptom Tickets went pr_open with no clickable PR — one even with no PR at all.

Fix Verify push and PR-creation results explicitly; a ticket is not pr_open until a human can click a link.

P2 · Everything worked — on my machine pipeline

Symptom First Linux CI run caught three bugs the Windows dev loop never saw (path handling, encodings).

Fix CI matrix runs the suite on Linux and Windows on every PR, forever after.

P3 · git commit refused our own pathspec pipeline

Symptom commit_all died: git rejects exclude pathspecs (

Fix Stage explicitly instead of exclude-pathspecs; regression test added.

P4 · One stale worktree poisoned every later run pipeline

Symptom After one crashed run, every subsequent run failed on the same leftover branch/worktree.

Fix Worker prunes stale worktrees and clears its own old branches before starting (agent-only branch guard — it may never touch human branches).

P5 · A batch ran the old runner pipeline

Symptom Fixes were merged and pushed, but the next batch behaved like pre-fix code.

Root cause The batch executed the working tree, and local main lagged origin/main.

Fix Every batch pins origin/main and greps the runner for a known marker before launching — refuse to run code you can't prove is current.

P6 · Runs died at the same step number, every time pipeline

Symptom Hard stop at a fixed step regardless of task size.

Root cause The token governor capped cumulative tokens across the whole loop instead of the context window — but every step resends the whole conversation, so the real wall is per-request context.

Fix Governor measures the next request's projected context, not the sum of all usage.

Lesson With chat-loop LLMs, "tokens used" and "tokens in context" are different quantities. Budget the second one.

P7 · The agent could declare victory with an empty diff pipeline

Symptom Runs ended completed with a confident summary and zero changed files.

Fix Judge runs by the diff and the gates, not by finish() (PR #10). A summary is a claim; the diff is the fact.

P8 · Tier router used facts that didn't exist yet pipeline

Symptom Escalation decisions referenced attempt history/blast data only available after routing.

Fix Route only on inputs that exist at routing time (PR #7); escalation happens between attempts, not inside one.

P9–P11 · The factory fixed its own bugs pipeline

Tickets 9 and 10 were real factory bugs filed as tickets, and the agent shipped the fixes: daily budget reset at UTC instead of local midnight (PR #17), and retries dying pushing to a stale remote branch (PR #18, with a test that proves retry clears the stale branch against a real bare git origin). Also: sync now reopens a ticket when its PR is reopened (PR #15), and transient git failures outside the pipeline are retried instead of escalated.

P12 · The pasted PAT died mid-build pipeline

Symptom Phase 2's first live tick: every GitHub call 401'd. The ghp_ token in factory.json had been revoked server-side — pasted tokens age out and die silently until the next unattended run discovers it at 3 a.m.

Root cause Two sources of GitHub identity: the gh CLI keyring login (alive, refreshing) and a hand-copied PAT in config (dead). The factory trusted the dead one.

Fix One credential: the scheduler wrapper resolves gh auth token at runtime; factory.json carries env:FACTORY_GH_TOKEN, never a secret. A missing variable expands to empty string so gh falls back to its keyring login and failures stay loud.

Lesson Unattended systems must authenticate through the one identity that can renew itself. A pasted secret is a scheduled outage.

P13 · The escalation path was dead code pipeline

Symptom First petro tickets exhausted their retries — and instead of escalating, the tick died with TypeError: finish() got an unexpected keyword argument 'error', leaving tickets stuck in running forever. The scheduler log filled with tracebacks from inside the error handler.

Root cause _escalate() called finish(error=…) (the parameter is detail=) and db.add_escalation(), which did not exist at all. Two consecutive crashes on the one path that runs only when everything else already failed. The unittest suite never exercised it — only the manual smoke.py script did, and nobody had run it since the db module was refactored.

Fix finish(detail=…); a real escalations table (ticket_id, why, created_at) so "what did it give up on, and why" is answerable from the DB; regression test that drives _escalate end to end and reads the row back.

Lesson A failure path tested only by a manual script is an untested failure path — and the escalation branch is the one you absolutely cannot discover broken at 3 a.m., because it is the only thing standing between a confused agent and a silently dropped ticket.

P14 · The PATH override that did nothing pipeline

Symptom A config agent.env override prepending a dependency venv to PATH looked applied (first PATH entry in the child env was the venv) yet bare python still resolved to the system interpreter.

Root cause Two stacked Windows traps. First, the base environment carries both PATH and Path; setting only one spelling leaves the twin to win the loader lookup. Second, subprocess.run(["python", …]) resolves bare names against the parent's PATH, not the child env block — while the agent's own run_command resolves via shutil.which(path=env["PATH"]), i.e. exactly the overridden path. A probe using the former concluded "broken"; the real tool chain was fine.

Fix minimal_env now deletes every case-twin of an overridden name before setting it, and expands a {PATH} placeholder so configs prepend without restating the search path. Probe with the same resolution the tool uses, not with a different one.

Lesson On Windows, environment variables are case-insensitive but not case-unique — an override that doesn't remove the twin is an override that may never be read. And verify through the same code path production uses.

P15 · The 1600-token ceiling made new files impossible pipeline

Symptom Even after the environment fix (A3), every petro run died at the step ceiling with zero changed files. The transcripts were worse than confusing — steps 8–20 were simply missing, as if the agent had been asleep.

Root cause Two harness bugs compounding. The per-step completion cap was hardcoded at 1600 tokens: a reasoning model spends ~1000 tokens thinking, and the tool-call JSON for a new 150-line test file needs 4–6k — so every write attempt was truncated before its JSON closed, the step came back as prose with no call, and the model never could create a file. (The factory's own tickets had survived only because they were small edit_file diffs.) And the loop's no-tool-call branch continued past the transcript write — the dead steps were invisible exactly where the diagnosis lived. A third run then hung 11 minutes: one request died and chat() retried 3×240 s with no awareness of the run's wall clock.

Fix LLM_STEP_MAX_TOKENS (default 6000) replaces the hardcoded cap; no-call steps are now transcribed with their prose; the transcript hole that hid them is closed.

Lesson An output cap sized for text replies silently disables the most important tool. And when a transcript shows fewer steps than the run counter, suspect the logger before the model — invisible steps hid the actual failure for two full debugging rounds.

P16 · Two ticks, one engine, mutual destruction pipeline

Symptom A manual tick and the 15-minute scheduler tick ran concurrently and each built a different ticket; both slowed toward the wall-clock cap (a trivial completion took 30 s mid-build).

Root cause The busy-guard (running_pids) was checked once at tick start; a tick begun while another was mid-build saw no running rows yet — or saw the other config's DB, which is a different file. On a single inference engine, concurrency is negative throughput: each stream halves the other's tokens/second until the 900 s cap kills both.

Fix process_once now takes a cross-process OS lock (msvcrt/fcntl, auto-released on process death — verified with a two-process probe) before claiming any ticket, below every entry point and across every config. Overlapping ticks return busy instead of stacking builds.

Lesson A guard that checks "is anything running" at startup only prevents races it happens to see; put the lock where the work starts, not where the scheduler decides. On one engine, one build — globally.

P17 · Three PRs opened on top of failing test suites pipeline

Symptom The first petro-tools PRs (#15, #16, #17) passed every local gate, opened, and then failed CI's e2e — on the agent's own test files. #15: 5 failures + 1 error of 6; #16: 2 of 15; #17: 8 of 21. The suites never passed on any platform.

Root cause The pre-PR gates checked the diff's shape (empty, junk, secrets, blast radius) but never ran anything. The agent's finish() is a claim, and the claim was false: it wrote tests and an implementation that disagreed, and nothing between the last edit and git push noticed.

Fix A test gate: gates.run_tests() executes the repo's configured gates.test_command in the worktree (with the agent's env overlay, so the pinned venv is used) before a PR opens. Failure = retry with the last 1,500 chars of output injected into the next attempt's "Previous failure" prompt; exhausted retries escalate. All three PRs were closed and their tickets re-queued with the exact assertion failures as context.

Lesson CI caught all three — the layered chain worked — but catching a false claim at CI costs a branch, a PR, and a human's glance. Run the cheapest decisive check at the cheapest point. And the flagged weak point ("the agent writes the tests its own code is judged by") is now mechanically bounded: the tests may be wrong, but they can no longer be red.

P18 · The unslop pass diffed against the engine URL pipeline

Symptom Caught by its own test before shipping: unslop.clean() returned the diff measured against http://192.168.68.73:8080/v1 — a git ref that does not exist.

Root cause Tuple-unpack clobbered a parameter: _, base, model = engine_from_cfg(...) overwrote the function's own base argument (the pre-agent SHA the final diff must be measured against). Every other path in the function looked right; only the last line was poisoned.

Fix Renamed the unpack targets (scfg, engine_base, model) and added a regression test that captures the base kwarg reaching diff_text() — verified by negative control: with the bug re-injected, exactly that test fails.

Lesson Never unpack into a name a parameter already owns; and a test earns belief only after you watch it fail on the bug it exists to catch.

Agent behavior

A1 · Six tickets, six attempts each, zero write calls agent

Symptom All "write tests for X" tickets died at ~24 steps having only read and searched. Transcripts showed perfect analysis, no edits.

Root cause Tool design: the only write tools were write_file (rewrite the entire 1,300-line test file — too big to emit) and edit_file (needs a perfect anchor). No append. The model chose endless exploration over an impossible write.

Fix Added append_file + a system-prompt rule: "To add a test class to a large existing file, use append_file; never rewrite a large file, and never keep exploring instead of editing." The same tickets then shipped on the first attempt.

Lesson What looks like model failure is often tool-design failure. Check what the agent was able to do before blaming what it "chose" to do.

A2 · The board looked empty (404) agent

Symptom Board URL returned 404 to an anonymous fetch; suspected empty project.

Root cause Personal GitHub Projects are private by default — 404 to logged-out fetchers. The repo was public; the board had 15 items all along. Not a bug: an auth wall wearing a 404 costume.

A3 · The ticket promised a dependency the environment didn't have agent

Symptom The first two petro tickets burned 6 attempts / $0.70 and produced zero file writes. Transcripts: steps 1–8 read the codebase (reasonable), then a slow spiral of pip list, where python, python --version, py -3.12 — environment archaeology until the token budget died.

Root cause The ticket body asserted "the environment already has openpyxl and PyMuPDF installed." It did not — the agent's python was the orchestrator's own interpreter, which had neither. The model correctly detected a contradiction between the spec and reality, and then, having no instruction for that state, investigated instead of writing. A small model trusts the environment over the prompt, then trusts the prompt over itself, and thrashes.

Fix Three parts: a dedicated venv (petro-tools-env, created with --copies — the default venv on this host is a uv-style trampoline that loses its venv context when resolved via PATH) with the deps installed; a config-driven agent.env overlay with {PATH} expansion so each repo pins its own toolchain; and an AGENTS.md rule: "never install packages, hunt for interpreters, or probe the environment — if an import fails, that is a bug in your code path, go straight to editing."

Lesson Before blaming the model for a failed ticket, verify the ticket's environment claims are true and count write calls in the transcript. An agent that explores instead of editing is reporting something: its ground floor is lying to it.

A4 · The reasoning loop: 6000 tokens of thinking, zero action agent

Symptom With the env fix and the 6k step cap in place, the agent finally wrote files — then stalled. 12 of 24 steps in one run ended at exactly 6000 tokens with no tool call and empty content: the whole output was the reasoning channel. Each looped step cost ~3 minutes; the run hit the 900 s wall again.

Root cause On long agent histories (mid-conversation, once the model must actually produce the module), this Qwen reasoning build falls into a thinking loop — it never reaches the answer. The old 1600 cap had been hiding it: truncating the thinking sometimes forced early action (which is also why it could never write files). A fresh-prompt A/B showed all variants fine — the loop only reproduces mid-conversation, so the probe had to replay the real transcript history against the engine.

Fix Measured replay at the exact loop point: baseline 6000 tok / no call; reasoning_effort=low 6000 tok / no call (not honored); chat_template_kwargs: {enable_thinking: false} → 1118 tokens, a clean write_file. New knob LLM_DISABLE_THINKING=1 (per-tier env, default off), set for both petro tiers.

Lesson A step that ends at exactly the output cap with no tool call is a loop signature — the no-call transcript line made it visible in one look. And knob experiments must replay the failure context: at step 1 every variant looks healthy.

A5 · With thinking off, the agent wandered instead of looping agent

Symptom After the thinking-off fix, one run spent all 32 steps searching the word "grade" across every file glob in the repo — **/*.md, **/*.json, **/*.yaml — and never edited anything. $0.08, zero files. The duplicate-call guard was evaded by varying the glob each time.

Root cause Explore-instead-of-edit (A1) in a new costume: nothing in the harness ever told the agent that reading forever is a failure. The no-call nudge only fires when a step makes no call — a search makes a call.

Fix A wander breaker in the agent loop: after LLM_WANDER_LIMIT (default 8) consecutive steps that change no file, the harness injects "STOP EXPLORING — next reply must be write_file/append_file/edit_file or finish", repeated every 4 steps. First run under it: 8 orientation steps, then a write at step 9 and 23 steps of real work.

Lesson Nudge on outcomes (files changed), not on message shape (tool calls made). A stream of plausible reads is indistinguishable from progress until you count what it produced.

A6 · An overnight engine outage spent retries like agent failures infra

Symptom Three tickets burned 3+1 attempts between 23:20 and 23:58, each attempt exactly 76 seconds and exactly $0.0000. Two escalated. The run details were identical: WinError 10060 — the engine host was unreachable (it fell asleep mid-evening).

Root cause The runner prints {"status": "error"} and exits 1 when the LLM is unreachable; the worker saw a non-zero exit, called it "fail", and consumed a retry. Retries are the budget for agent mistakes — infrastructure downtime drained it in four minutes flat.

Fix agent.run now sniffs the runner's inner JSON status: an inner error surfaces as outer error, and the worker re-queues the ticket untouched — "deferred (engine unreachable)", no attempt burned, no failure injected into the next prompt. The three damaged tickets were reset; the outage had cost them nothing.

Lesson Every retry must answer "did the agent fail?" — anything else (engine down, network, disk) is a pause, not a strike. A queue that confuses downtime with incompetence escalates tickets that never made a single LLM call.

A7 · The reviewer's JSON never arrived infra

Symptom The first live AI reviews returned "review unparseable" — but a manual call with the same prompt parsed fine. Non-deterministic, maddening.

Root cause Two stacked bugs. The one-shot client sent enable_thinking: false at the top level of the request; llama.cpp only honours it inside chat_template_kwargs — so the model streamed its whole reasoning into content and hit the 400-token cap before emitting the JSON verdict. And the parser used a greedy first-brace-to-last-brace match, which breaks whenever stray braces precede the object.

Fix chat_template_kwargs for the thinking flag, 900-token budget, and llmclient.extract_json() — brace-balanced candidates first, greedy only as fallback. Live re-run: approve on both real petro diffs with accurate notes, and correctly concerns when deliberately fed a mismatched diff.

Lesson Engine quirks learned once (thinking-off, robust JSON extraction) must live in one shared client — every new agent that re-implements them rediscovers them in production.

A8 · The secret redactor ate a line of code infra

Symptom A freshly written module failed to compile with SyntaxError: '(' was never closed — but every read of the file showed a perfectly valid line.

Root cause The file-writing toolchain redacts secret-looking patterns on the way in: api_key=*** in the payload landed on disk as literal api_key=*** — and the display path redacts it again, so the file always looked correct. Three "fixes" were sent and "verified" against the redacted view before repr() of the raw bytes told the truth.

Fix Rebuilt the line programmatically (string concatenation defeats the pattern match) and let py_compile, not the display, be the arbiter.

Lesson When a tool's view of a file and the file itself can differ, trust only the compiler. Never write literal secret-shaped name=value tokens into code through redacting tools.

Ticket specs — the real ceiling

T1 · Eight failed attempts, and the bug was in the ticket spec

Symptom Ticket 13 ("tests for local-midnight spend_today") failed 8 attempts / $1.37 while other tickets shipped for pennies.

Root cause The ticket body told the agent to fake time.localtime/struct_time/gmtoff — while the function under test takes an injectable epoch float. The spec pushed the model into the one corner where a 4B-class model can't dance.

Fix Closed 13; split into tickets 16/17 with explicit class names, the seam named ("pass now=; do NOT patch time"), and "use append_file". Both shipped first try, $0.06 and $0.09.

Lesson Ticket quality dominates model quality. Name the seam, forbid the trap, size the ticket to the tier.

T2 · A ticket with no passing solution spec

Symptom Ticket 19 failed 3 attempts even after the A1/T1 fixes.

Root cause My ticket body asserted an upper bound on a started_at >= sum — mathematically impossible — and the test was redundant with ticket 18's boundary test anyway. The agent thrashed against an unsatisfiable spec.

Fix Closed as spec bug with the reason recorded. Rule added to the skill: hand-solve a ticket on one line before queueing it; if the spec has no passing solution, no tier can find one.

T3 · The first customer ticket referenced a module its dependency would write spec

Symptom petro-tools ticket 1 (audit) escalated after 3 attempts. Its body said "resolve blocks with the SAME petro.dips.resolve_blocks the filler uses" — a function ticket 6 was supposed to create. Filing order was not build order, and the queue drains by id.

Root cause The backlog was filed as a list of features, not a dependency graph. The agent dutifully improvised resolve_blocks inside dips.py, hit the openpyxl trap the real spec handles (synthetic workbooks store dates as =A5+1 formulas with no cached values, so data_only=True reads None — the chain must be resolved arithmetically from the anchor), and failed the same assertion three times.

Fix A seq column on tickets: claim_next orders by seq, id, and the petro backlog was reordered into dependency order (parsers → csvio → scan → shifts → dips → audit → docs). Ticket 6's spec already contained the formula-chain knowledge — the lesson is to file the dependency before the dependent, not to restate the dependency's contract in every ticket.

Lesson A queue is a build system the moment tickets reference each other's modules. Filing order is a coincidence; dependency order is a fact — store it.

P9 · Every PR conflicted with code already on main pipeline

Symptom On the dashboard customer, five consecutive tickets produced PRs that re-implemented modules already merged (load_rows, render_index) and conflicted on open. Each agent behaved rationally — its worktree genuinely did not contain the merged code.

Root cause worktree.create() branched from the local clone's HEAD, which nothing ever fetched. The local main sat at the scaffold commit all day while GitHub moved thirteen merges ahead. The human merge gate made the lag permanent: the longer PRs wait for a person, the staler a HEAD-based branch gets.

Fix Fetch, then branch from origin/<default> (resolved via symbolic-ref refs/remotes/origin/HEAD); a failed fetch falls back instead of blocking. Regression-tested with a bare-remote fixture where the local clone is deliberately behind.

Lesson With a human merge gate, the remote — not the local checkout — is the trunk. A build system that reads its own base from a cache is reading fiction.

P10 · The mutation gate mutated the tests it depended on pipeline

Symptom A test-only ticket (add a Chromium browser test) scored 0/12 mutants killed and escalated; the retry rewrote product code it was told to leave alone.

Root cause The gate built mutants from every added line in the diff — including lines inside the new test file. A mutant inside a test cannot be killed by that same test (it fails to run or asserts its own broken logic), so a test-only diff scores an impossible zero, and the failure message ("survived: tests/test_x.py") goaded the next attempt into touching product code.

Fix The gate skips test files (tests/ prefix or test_ basename). Tests are the weapon in this gate, never the target. Regression test: a tests-only diff returns ok with "no candidates".

Lesson Every metric needs a domain check: an impossible score is a broken instrument, not a failed agent.

Distilled lessons

  1. Judge artifacts, not self-reports. The diff and the gates decide; finish() is marketing.
  2. Test the gates against adversarial examples. PR #37 (zero tests, binary junk, green CI) is the template: every gate needs a change that must trip it.
  3. Context window ≠ cumulative tokens. Budget the per-request context in a chat loop.
  4. Tool design shapes behavior. No append tool → endless exploration. Fix the tool before blaming the model.
  5. The ticket body is part of the system. Hand-solve before queueing; name the seam; forbid the trap; size to the tier.
  6. Dual-OS CI from day one. Windows-only dev loops ship Linux-broken code.
  7. Status changes require a clickable truth. No pr_open without a URL a human can open.
  8. Pin what you execute. A batch must prove it runs current code (origin/main + marker grep).
  9. Fail the attempt, not the ticket. Junk/binary diffs retry; only spec bugs close.
